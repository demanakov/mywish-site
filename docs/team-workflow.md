## Где работают интеграции

В проекте сохранены отправка на `/api/leads.php`, согласие, UTM, yclid, ClientID,
обработка ошибок и защита от повторной заявки. PHP на Beget сохраняет данные в SQLite
и отправляет их в amoCRM и Telegram. Токены, база и закрытая конфигурация остаются на сервере.

Дмитрию не нужен доступ к рабочим токенам для изменения текстов, фото, меню и дизайна.
Локальный Next.js и статический предпросмотр не запускают PHP: обычное нажатие
«Отправить» локально не создаёт реальную заявку. Автоматические проверки формы
подменяют ответ API и проверяют интерфейс без сделок и уведомлений.
Рабочую доставку проверяем отдельно на сервере, когда меняется обработка заявок.

Нельзя заменять интегрированный `RequestForm.tsx` старой заглушкой, терять адаптер
`src/lib/lead-payload.mjs`, атрибуцию, согласия или серверное подтверждение успеха.
Изменения этих файлов нужно явно отмечать при передаче.

## Работа Дмитрия

Для первого запуска нужны Git и Node.js 24 с npm. Для браузерных проверок формы
и калькулятора нужен установленный Google Chrome: тесты используют канал `chrome`.

1. Получить принятую интегрированную версию и создать отдельную ветку для доработки.
2. Выполнить `npm ci`, затем `npm run dev` и работать на `http://localhost:3000`.
3. Проверить результат командой `npm run check`. Для просмотра собранной версии
   остановить dev-сервер и запустить `npm start`.
4. Во втором терминале проверить форму и калькулятор:

```bash
BASE_URL=http://127.0.0.1:3000 npm run test:integration
BASE_URL=http://127.0.0.1:3000 npm run test:calculator
```

5. Отправить ветку в GitHub и открыть pull request. Передать Денису ссылку,
   полный хеш коммита, короткий список правок и скриншоты компьютера и телефона.
   Указать результаты проверок и отдельно – изменения формы или интеграций.
6. Дождаться обратной связи. Публикация на основной сайт остаётся за Денисом.

Если GitHub временно недоступен, можно передать ZIP исходников вместе с хешем
исходного коммита и списком изменений. `node_modules`, `.next`, базы, токены и ключи
в ZIP не включаются. Основной способ для регулярной работы – ветки и pull request.

## Приёмка и публикация

1. Мы получаем конкретный коммит, смотрим изменения и проверяем сборку,
   форму, калькулятор, ссылки и размеры 1280×900, 477×844, 360×800.
2. Денис смотрит результат и даёт поручение опубликовать именно эту версию.
3. Перед деплоем делаем резервную копию изменяемых файлов и консистентный снимок SQLite.
4. Собираем согласованный коммит и загружаем `out/` на Beget по SSH.
   Заменяем главную последней, сохраняем существующие дополнительные страницы и backend.
5. Проверяем опубликованную версию и фиксируем коммит, дату, резервную копию и результат.

В репозитории используются автоматические проверки, а не автоматическая публикация.
Серверные ключи в GitHub Actions для этого процесса не нужны.
Инструкция для выполняющего деплой: [crm-and-deploy.md](crm-and-deploy.md).
